# MySQL数据库访问行为异常审计方案

## 一、背景与挑战

### 1.1 项目目标
- 覆盖黑客入侵行为、内部人员异常操作、异常导出、异常查询
- **区分人员和系统查询**（核心需求）
- 指标要求：异常检出率 98%，召回率 > 95%

### 1.2 数据源现状

| 数据源 | 可用字段 | 局限性 |
|--------|----------|--------|
| 堡垒机日志 | 用户身份、连接时间、目标数据库 | 无具体SQL命令 |
| dbproxy日志 | SQL语句、来源IP、系统账号、时间戳 | 无人员身份信息 |

### 1.3 样本日志分析结果（200条样本）

**账号特征：**
- 99% 账号以 `_rw` 结尾（读写账号）
- 65% 账号包含随机字符串模式（如 `u25r4b`, `nj3bgr`）—— **系统自动生成特征**
- IP与账号呈现 1:1 映射关系

**SQL特征：**
- 20.5% SQL包含 `traceid` —— **系统请求强特征**
- 37.5% SQL包含 JSON注释 —— **系统请求特征**
- 26% SQL使用绑定变量(`?`) —— **预编译语句，系统请求特征**
- 平均SQL长度 845 字符

## 二、核心问题：人员与SQL的关联

### 2.1 关联难点
堡垒机和dbproxy之间**缺少直接关联字段**，需要通过间接方式建立关联。

### 2.2 可能的关联方案（需确认）

**方案A：IP+时间窗口关联**
- 前提：堡垒机日志包含用户访问数据库的IP和时间
- 方法：用户登录IP + 时间窗口 → 匹配dbproxy中的client_ip
- 可行性：需确认堡垒机日志是否记录了用户的出口IP

**方案B：账号归属映射表**
- 前提：存在账号归属配置（哪个系统/人员拥有哪个账号）
- 方法：建立账号→系统/人员的映射关系
- 可行性：需确认是否有CMDB或账号管理系统

**方案C：网络层关联**
- 前提：能获取NAT映射或会话日志
- 方法：通过防火墙/NAT日志关联用户真实IP和内网IP
- 可行性：需确认网络架构和日志可用性

## 三、人员vs系统查询识别方案

### 3.1 多维度识别模型

基于样本分析，我建议采用**规则+机器学习混合模型**：

#### 维度1：SQL语法特征（权重高）

| 特征 | 系统查询 | 人员查询 | 权重 |
|------|----------|----------|------|
| 包含traceid | ✓ | ✗ | 高 |
| JSON注释头 | ✓ | 通常无 | 高 |
| 绑定变量(?) | ✓ | 通常无 | 中 |
| LIMIT 1 | 常见 | 少见 | 低 |
| SELECT * | 少见 | 常见 | 中 |
| 手写格式 | 无 | ✓ | 低 |

#### 维度2：账号命名模式（权重高）

```
系统账号模式：
- 包含随机串：xxx_u25r4b_rw, xxx_nj3bgr_rw
- 服务标识：xxx_api_rw, xxx_service_rw

人员账号模式：
- 真实姓名：zhangsan_rw, lisi_rw
- 工号：emp12345_rw
```

#### 维度3：行为模式（权重中）

| 特征 | 系统查询 | 人员查询 |
|------|----------|----------|
| 时间分布 | 24小时均匀 | 工作时间集中 |
| 查询频率 | 高频规律 | 低频不规律 |
| IP分布 | 固定少数IP | 可能多变 |
| 返回行数 | 通常有limit | 可能大量导出 |

### 3.2 识别规则示例

```python
def is_system_query(record):
    score = 0

    # SQL特征
    if 'traceid' in record['sql'].lower():
        score += 30
    if record['sql'].startswith('/*{'):
        score += 20
    if '?' in record['sql']:
        score += 10

    # 账号特征
    if re.search(r'_[a-z0-9]{6}_rw$', record['account']):
        score += 25

    # 行为特征
    if record['hour'] in [0,1,2,3,4,5,22,23]:  # 深夜
        score += 5

    return score >= 50  # 阈值可调
```

## 四、异常检测方案

### 4.1 检测场景覆盖

| 场景 | 检测方法 | 特征 |
|------|----------|------|
| **黑客入侵** | SQL注入检测、异常IP、异常时间 | SQL语法异常、非授权IP |
| **内部异常操作** | 行为基线偏离 | 异常表、异常操作类型、异常量 |
| **异常导出** | 结果集监控 | 大量返回行、敏感字段访问 |
| **异常查询** | 频率+内容分析 | 高频查询、全表扫描 |

### 4.2 技术架构建议

```
┌─────────────────────────────────────────────────────────┐
│                    数据采集层                            │
│  堡垒机日志 + dbproxy日志 + (可选)CMDB/账号系统          │
└─────────────────────────────────────────────────────────┘
                           ↓
┌─────────────────────────────────────────────────────────┐
│                    数据处理层                            │
│  日志解析 → 人员关联 → 特征提取 → 标签识别              │
└─────────────────────────────────────────────────────────┘
                           ↓
┌─────────────────────────────────────────────────────────┐
│                    检测引擎层                            │
│  规则引擎(快速) + ML模型(精准) + 实时流处理             │
└─────────────────────────────────────────────────────────┘
                           ↓
┌─────────────────────────────────────────────────────────┐
│                    告警响应层                            │
│  告警聚合 → 风险评分 → 工单/通知 → 审计报告             │
└─────────────────────────────────────────────────────────┘
```

### 4.3 关键技术组件

1. **人员关联服务**：IP/账号→人员的映射引擎
2. **SQL解析器**：提取表名、字段、操作类型、风险等级
3. **特征计算引擎**：实时计算行为特征
4. **异常检测模型**：
   - 规则库：已知攻击模式、合规规则
   - 统计模型：行为基线、异常检测
   - ML模型（可选）：无监督聚类、有监督分类

### 4.4 大数据架构方案（日均>100万SQL）

**技术栈：复用现有平台（PySpark + Hive SQL）**

```
┌────────────────────────────────────────────────────────────┐
│                     数据采集层                              │
│  dbproxy日志 → HDFS/Hive → 分区表(按天/小时)              │
│  账号归属表 → MySQL配置表 → 定时同步到Hive                 │
└────────────────────────────────────────────────────────────┘
                            ↓
┌────────────────────────────────────────────────────────────┐
│                     离线处理层 (PySpark)                    │
│  SQL解析 → 特征提取 → 人员/系统识别 → 异常检测            │
│  调度方式：Airflow/定时任务，每小时/每天执行               │
└────────────────────────────────────────────────────────────┘
                            ↓
┌───────────────────┬────────────────────────────────────────┐
│   准实时告警路径   │          离线分析路径                   │
│  小时级Spark任务   │  日级Spark任务                        │
│  → 高危规则匹配    │  → 行为基线计算                       │
│  → MySQL/告警接口  │  → 模型训练 + 报表                    │
└───────────────────┴────────────────────────────────────────┘
```

**存储方案：**
- **源数据层**：Hive分区表（dbproxy_log, account_mapping）
- **结果层**：Hive（审计结果）+ MySQL（告警记录、配置）
- **可选增强**：如需秒级实时，可引入Kafka+Flink组件

**混合检测模式：**
| 模式 | 延迟 | 覆盖场景 | 实现方式 |
|------|------|----------|----------|
| 准实时 | 小时级 | SQL注入、敏感表访问、异常导出 | PySpark每小时任务 |
| 离线 | T+1 | 行为基线、异常模式挖掘 | PySpark日级任务 |

**计算资源估算（参考）：**
- Spark Executor：5-10个，每个4核16G
- Hive表分区：按天分区，保留180天
- 告警存储：MySQL，保留1年

## 七、实施路径建议（基于PySpark+Hive技术栈）

### Phase 1：数据接入与基础识别（2-3周）
**目标：建立数据管道，实现人员/系统识别**

| 任务 | 交付物 | 周期 |
|------|--------|------|
| 日志接入Hive | 分区表 + 数据同步脚本 | 3天 |
| 账号归属表导入 | MySQL配置表 + Hive同步 | 2天 |
| SQL解析器开发 | PySpark UDF：表名/操作类型提取 | 1周 |
| 人员/系统识别模型 | Hive SQL + 评分规则 | 3天 |
| 基础报表 | 异常查询日报告 | 2天 |

**验收标准：**
- 日志T+1入Hive
- 人员/系统识别准确率 >90%

### Phase 2：规则检测上线（2-3周）
**目标：覆盖主要异常场景**

| 检测场景 | 规则示例 | 实现方式 |
|----------|----------|----------|
| SQL注入 | 语法异常、敏感函数 | PySpark SQL解析 |
| 敏感表访问 | 配置表清单 | Hive JOIN + 规则匹配 |
| 大量导出 | result_lines > 阈值 | Hive聚合统计 |
| 异常时间访问 | 非工作时间 + 敏感操作 | 时间函数 + 规则 |
| 异常IP访问 | IP白名单校验 | 配置表JOIN |

**验收标准：**
- 规则覆盖核心场景
- 每日告警推送到指定渠道

### Phase 3：基线与模型优化（3-4周）
**目标：建立行为基线，提升检出率/召回率**

| 任务 | 方法 | 目标 |
|------|------|------|
| 正常行为基线 | Hive SQL统计各维度分布 | 减少误报 |
| 异常检测模型 | PySpark ML (Isolation Forest) | 发现未知异常 |
| 标注数据收集 | 专家标注 + 反馈 | 构建训练集 |
| 有监督模型（可选） | XGBoost (PySpark) | 提升准确率 |

**验收标准：**
- 异常检出率 ≥ 98%
- 召回率 ≥ 95%

### Phase 4：持续运营（长期）
- 规则迭代优化
- 新场景覆盖
- 模型版本更新
- 安全事件复盘

## 九、总结

### 核心思路

**人员 vs 系统识别 = 账号归属表 + SQL特征 + 行为模式**

1. **第一层：账号归属表**（强信号）
   - 有文档记录的账号 → 直接判定
   - 人工维护的账号命名规范 → 规则识别

2. **第二层：SQL语法特征**（中等信号）
   - traceid → 系统请求（准确率~95%）
   - JSON注释头 → 系统请求
   - 绑定变量 → 系统请求（有少量误判）
   - 手写风格 → 人员请求

3. **第三层：行为模式**（辅助信号）
   - 时间分布、查询频率、返回行数等

### 检出率98%、召回率95%的实现路径

| 阶段 | 检出率 | 召回率 | 关键措施 |
|------|--------|--------|----------|
| Phase 1 | 60% | 80% | 基础规则 + 账号映射 |
| Phase 2 | 85% | 90% | 规则完善 + 场景覆盖 |
| Phase 3 | 95% | 95% | 行为基线 + 异常检测模型 |
| Phase 3+ | 98% | 95%+ | 持续优化 + 反馈闭环 |
