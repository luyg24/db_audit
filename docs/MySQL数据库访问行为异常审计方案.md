# MySQL数据库访问行为异常审计方案

## 一、背景与挑战

### 1.1 项目目标
- 覆盖黑客入侵行为、内部人员异常操作、异常导出、异常查询
- **区分人员和系统查询**（核心需求）
- 指标要求：异常检出率 98%，召回率 > 95%

### 1.2 数据源现状

| 数据源 | 可用字段 | 局限性 |
|--------|----------|--------|
| 堡垒机日志 | 用户身份、连接时间、目标数据库 | 无具体SQL命令 |
| dbproxy日志 | SQL语句、来源IP、系统账号、时间戳 | 无人员身份信息 |

### 1.3 样本日志分析结果（200条样本）

**账号特征：**
- 99% 账号以 `_rw` 结尾（读写账号）
- 65% 账号包含随机字符串模式（如 `u25r4b`, `nj3bgr`）—— **系统自动生成特征**
- IP与账号呈现 1:1 映射关系

**SQL特征：**
- 20.5% SQL包含 `traceid` —— **系统请求强特征**
- 37.5% SQL包含 JSON注释 —— **系统请求特征**
- 26% SQL使用绑定变量(`?`) —— **预编译语句，系统请求特征**
- 平均SQL长度 845 字符

## 二、核心问题：人员与SQL的关联

### 2.1 关联难点
堡垒机和dbproxy之间**缺少直接关联字段**，需要通过间接方式建立关联。

### 2.2 可能的关联方案（需确认）

**方案A：IP+时间窗口关联**
- 前提：堡垒机日志包含用户访问数据库的IP和时间
- 方法：用户登录IP + 时间窗口 → 匹配dbproxy中的client_ip
- 可行性：需确认堡垒机日志是否记录了用户的出口IP

**方案B：账号归属映射表**
- 前提：存在账号归属配置（哪个系统/人员拥有哪个账号）
- 方法：建立账号→系统/人员的映射关系
- 可行性：需确认是否有CMDB或账号管理系统

**方案C：网络层关联**
- 前提：能获取NAT映射或会话日志
- 方法：通过防火墙/NAT日志关联用户真实IP和内网IP
- 可行性：需确认网络架构和日志可用性

## 三、人员vs系统查询识别方案

### 3.1 多维度识别模型

基于样本分析，我建议采用**规则+机器学习混合模型**：

#### 维度1：SQL语法特征（权重高）

| 特征 | 系统查询 | 人员查询 | 权重 |
|------|----------|----------|------|
| 包含traceid | ✓ | ✗ | 高 |
| JSON注释头 | ✓ | 通常无 | 高 |
| 绑定变量(?) | ✓ | 通常无 | 中 |
| LIMIT 1 | 常见 | 少见 | 低 |
| SELECT * | 少见 | 常见 | 中 |
| 手写格式 | 无 | ✓ | 低 |

#### 维度2：账号命名模式（权重高）

```
系统账号模式：
- 包含随机串：xxx_u25r4b_rw, xxx_nj3bgr_rw
- 服务标识：xxx_api_rw, xxx_service_rw

人员账号模式：
- 真实姓名：zhangsan_rw, lisi_rw
- 工号：emp12345_rw
```

#### 维度3：行为模式（权重中）

| 特征 | 系统查询 | 人员查询 |
|------|----------|----------|
| 时间分布 | 24小时均匀 | 工作时间集中 |
| 查询频率 | 高频规律 | 低频不规律 |
| IP分布 | 固定少数IP | 可能多变 |
| 返回行数 | 通常有limit | 可能大量导出 |

### 3.2 识别规则示例

```python
def is_system_query(record):
    score = 0

    # SQL特征
    if 'traceid' in record['sql'].lower():
        score += 30
    if record['sql'].startswith('/*{'):
        score += 20
    if '?' in record['sql']:
        score += 10

    # 账号特征
    if re.search(r'_[a-z0-9]{6}_rw$', record['account']):
        score += 25

    # 行为特征
    if record['hour'] in [0,1,2,3,4,5,22,23]:  # 深夜
        score += 5

    return score >= 50  # 阈值可调
```

## 四、异常检测方案

### 4.1 检测场景覆盖

| 场景 | 检测方法 | 特征 |
|------|----------|------|
| **黑客入侵** | SQL注入检测、异常IP、异常时间 | SQL语法异常、非授权IP |
| **内部异常操作** | 行为基线偏离 | 异常表、异常操作类型、异常量 |
| **异常导出** | 结果集监控 | 大量返回行、敏感字段访问 |
| **异常查询** | 频率+内容分析 | 高频查询、全表扫描 |

### 4.2 技术架构建议

```
┌─────────────────────────────────────────────────────────┐
│                    数据采集层                            │
│  堡垒机日志 + dbproxy日志 + (可选)CMDB/账号系统          │
└─────────────────────────────────────────────────────────┘
                           ↓
┌─────────────────────────────────────────────────────────┐
│                    数据处理层                            │
│  日志解析 → 人员关联 → 特征提取 → 标签识别              │
└─────────────────────────────────────────────────────────┘
                           ↓
┌─────────────────────────────────────────────────────────┐
│                    检测引擎层                            │
│  规则引擎(快速) + ML模型(精准) + 实时流处理             │
└─────────────────────────────────────────────────────────┘
                           ↓
┌─────────────────────────────────────────────────────────┐
│                    告警响应层                            │
│  告警聚合 → 风险评分 → 工单/通知 → 审计报告             │
└─────────────────────────────────────────────────────────┘
```

### 4.3 关键技术组件

1. **人员关联服务**：IP/账号→人员的映射引擎
2. **SQL解析器**：提取表名、字段、操作类型、风险等级
3. **特征计算引擎**：实时计算行为特征
4. **异常检测模型**：
   - 规则库：已知攻击模式、合规规则
   - 统计模型：行为基线、异常检测
   - ML模型（可选）：无监督聚类、有监督分类

### 4.4 大数据架构方案（日均>100万SQL）

**技术栈：复用现有平台（PySpark + Hive SQL）**

```
┌────────────────────────────────────────────────────────────┐
│                     数据采集层                              │
│  dbproxy日志 → HDFS/Hive → 分区表(按天/小时)              │
│  账号归属表 → MySQL配置表 → 定时同步到Hive                 │
└────────────────────────────────────────────────────────────┘
                            ↓
┌────────────────────────────────────────────────────────────┐
│                     离线处理层 (PySpark)                    │
│  SQL解析 → 特征提取 → 人员/系统识别 → 异常检测            │
│  调度方式：Airflow/定时任务，每小时/每天执行               │
└────────────────────────────────────────────────────────────┘
                            ↓
┌───────────────────┬────────────────────────────────────────┐
│   准实时告警路径   │          离线分析路径                   │
│  小时级Spark任务   │  日级Spark任务                        │
│  → 高危规则匹配    │  → 行为基线计算                       │
│  → MySQL/告警接口  │  → 模型训练 + 报表                    │
└───────────────────┴────────────────────────────────────────┘
```

**存储方案：**
- **源数据层**：Hive分区表（dbproxy_log, account_mapping）
- **结果层**：Hive（审计结果）+ MySQL（告警记录、配置）
- **可选增强**：如需秒级实时，可引入Kafka+Flink组件

**混合检测模式：**
| 模式 | 延迟 | 覆盖场景 | 实现方式 |
|------|------|----------|----------|
| 准实时 | 小时级 | SQL注入、敏感表访问、异常导出 | PySpark每小时任务 |
| 离线 | T+1 | 行为基线、异常模式挖掘 | PySpark日级任务 |

**计算资源估算（参考）：**
- Spark Executor：5-10个，每个4核16G
- Hive表分区：按天分区，保留180天
- 告警存储：MySQL，保留1年

## 六、人员/系统识别方案调整

### 6.1 问题澄清

```
之前假设：账号 → 单一归属（人或系统）
实际情况：账号 → 公用账号（多人+多系统共用）
```

**结论**：不能通过账号归属表直接区分人员/系统，需要其他维度。

### 6.2 新的识别维度

| 维度 | 区分能力 | 数据来源 | 当前状态 |
|------|----------|----------|----------|
| **SQL特征** | 高 | traceid/JSON注释 | ✅ 可实现 |
| **IP地址段** | 高 | 服务器IP vs 办公网IP | ⏳ 待数据 |
| **堡垒机会话** | 高 | 用户登录IP+时间 | ⏳ 待数据 |
| **时间模式** | 中 | 深夜高频→系统 | ✅ 可实现 |

### 6.3 识别优先级调整

```
优先级1: SQL特征判断（当前可实现）
         - traceid → 系统（准确率~95%）
         - JSON注释头 → 系统

优先级2: IP地址判断（待数据）
         - 服务器IP → 系统
         - 办公网IP → 人员

优先级3: 堡垒机会话关联（待数据）
         - 登录记录 → 人员身份
```

## 八、实施路径建议（基于PySpark+Hive技术栈）

### Phase 1：SQL模板化与语义分析（1-2周）⭐ 当前优先
**目标：建立SQL核心处理能力，不依赖外部数据**

**为什么优先做这个：**
- 不依赖账号归属表、IP段等外部数据
- 可直接处理dbproxy日志
- 是后续所有检测的基础能力

| 任务 | 交付物 | 周期 |
|------|--------|------|
| SQL模板化函数 | 模板提取 + 哈希计算 + 单元测试 | 2天 |
| sqlparse语义分析 | SQL结构解析UDF + 字段提取 | 3天 |
| 模板聚合统计 | 日志SQL → 模板分布统计 | 2天 |
| 模板基线表设计 | Hive表结构 + 基线计算逻辑 | 2天 |
| 新模板检测规则 | 未见模板告警 + 频率偏离告警 | 2天 |

**验收标准：**
- 100万SQL聚合为模板后 <1万条
- SQL注入检出率 >90%
- 敏感字段识别准确率 >85%

### Phase 2：异常检测规则上线（1-2周）
**目标：基于模板和语义分析，上线检测规则**

| 检测场景 | 规则示例 | 实现方式 |
|----------|----------|----------|
| SQL注入 | 语义分析 + 模式匹配 | sqlparse + 规则 |
| 敏感表访问 | 配置表清单 | Hive JOIN + 规则匹配 |
| 敏感字段访问 | 语义解析字段 | sqlparse提取字段 |
| 大量导出 | result_lines > 阈值 | Hive聚合统计 |
| 新模板检测 | 模板不在基线表 | 模板哈希匹配 |
| 频率异常 | 超过基线3倍标准差 | 统计计算 |

**验收标准：**
- 规则覆盖核心场景
- 每日告警推送到指定渠道

### Phase 3：人员/系统识别优化（待数据就绪）
**目标：基于IP段+SQL特征区分人员/系统查询**

**前置依赖：**
- 服务器IP段/清单
- 办公网IP段
- 堡垒机日志（可选）

| 任务 | 交付物 | 周期 |
|------|--------|------|
| IP段配置管理 | 服务器IP段 + 办公网IP段配置 | 1天 |
| IP判断逻辑 | IP → 人员/系统判定 | 1天 |
| SQL特征识别优化 | traceid/JSON注释检测增强 | 2天 |
| 堡垒机关联（可选） | 会话IP+时间 → 用户身份 | 3天 |
| 综合评分模型 | 多维度融合判定 | 2天 |

**验收标准：**
- 人员/系统识别准确率 >85%

### Phase 4：基线与模型优化（3-4周）
**目标：建立行为基线，提升检出率/召回率**

| 任务 | 方法 | 目标 |
|------|------|------|
| 正常行为基线 | Hive SQL统计各维度分布 | 减少误报 |
| 异常检测模型 | PySpark ML (Isolation Forest) | 发现未知异常 |
| 标注数据收集 | 专家标注 + 反馈 | 构建训练集 |
| 有监督模型（可选） | XGBoost (PySpark) | 提升准确率 |

**验收标准：**
- 异常检出率 ≥ 98%
- 召回率 ≥ 95%

- 规则迭代优化
- 新场景覆盖
